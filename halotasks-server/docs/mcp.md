# HaloTask Pro MCP Phase 1

## Scope

Phase 1 exposes a read-only Model Context Protocol endpoint at:

`/mcp`

Transport: Streamable HTTP using the MCP TypeScript SDK v2.

The MCP layer is intentionally thin:

```
MCP client
   |
   | authenticated HTTP
   v
/mcp
   |
   | existing HaloTask JWT/session validation
   v
MCP read tools
   |
   v
user-scoped HaloTask task model
   |
   v
MongoDB
```

MCP does not receive direct database credentials and does not bypass HaloTask authentication.

## Authentication

The endpoint uses the existing `Authorization: Bearer <JWT>` authentication middleware.

That means:

- the token signature is verified with the existing `JWT_SECRET`;
- the current account `tokenVersion` is checked;
- revoked sessions are rejected;
- every MCP query is scoped to the authenticated user's id;
- there is no server-wide MCP secret.

OAuth/revocable MCP-specific credentials are deliberately deferred to the later authentication phase.

## Phase 1 tools

| Tool | Purpose | Writes |
| --- | --- | --- |
| `halo_get_project_context` | Workspace/project context derived from current task data | No |
| `halo_list_tasks` | Paginated, filtered user-owned tasks | No |
| `halo_get_task` | One user-owned task | No |
| `halo_list_subtasks` | Embedded subtasks for a user-owned task | No |
| `halo_get_project_summary` | Aggregate task/workspace summary | No |

Dependencies and comments are not exposed because the current HaloTask data model does not contain first-class models for them.

The current model also does not contain a first-class Project entity. The project/context tools therefore describe the authenticated user's HaloTask workspace from task data rather than inventing project records that do not exist.

## Security properties

The MCP tools are registered with read-only annotations.

Phase 1 contains no task creation, update, deletion, tree mutation, history mutation, or other write tool.

Task responses are projected before leaving the server. Internal `userId` and other non-MCP fields are not returned merely because they happen to exist in the MongoDB document.

## Local verification

From `halotasks-server/`:

```bash
npm install
npm run test
npm run typecheck
npm run typecheck:tests
npm run build
```

Then start the server normally and verify `POST /mcp` with an authenticated HaloTask JWT.

The branch intentionally does not claim automated verification from the development environment used to prepare this PR. The dependency lockfile should be regenerated by the repository's normal npm workflow before merge.
